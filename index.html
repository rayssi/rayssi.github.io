Ma démarche qualitéHow I build quality

La même méthode, que la QA existe déjà ou qu’elle soit à construire de zéro. La qualité commence avant le code (shift-left) et se mesure jusqu’en production.

The same method, whether QA already exists or has to be built from scratch. Quality starts before the code (shift-left) and is measured all the way to production.

Fiabilité et vitesse des testsTest reliability and speed

  • Page Object Model : sélecteurs et actions de chaque écran isolés, une évolution d’interface se corrige à un seul endroit.
  • Retry maîtrisé : un test en échec est relancé automatiquement, et un test qui ne passe qu’au second essai est compté comme flaky dans les KPI, jamais masqué.
  • Exécution parallèle (multi-threading, workers) : des scénarios indépendants lancés en même temps pour réduire la durée des runs.
  • Données générées par API : chaque test crée ses propres données, sans dépendre d’un ordre d’exécution ni d’un état partagé.
  • Tags : exécution ciblée par client, projet ou environnement selon le contexte du pipeline.
  • Code de test traité comme du code produit : linting Ruff, revue de code, conventions documentées.
  • Page Object Model: each screen’s selectors and actions are isolated, so a UI change is fixed in one place.
  • Controlled retries: a failing test is re-run automatically, and a test that only passes on the second try counts as flaky in the KPIs, never hidden.
  • Parallel execution (multi-threading, workers): independent scenarios run at the same time to cut run time.
  • API-generated data: each test creates its own data, with no dependency on run order or shared state.
  • Tags: targeted runs by client, project or environment depending on the pipeline context.
  • Test code treated like product code: Ruff linting, code review, documented conventions.

Quality gates

  1. Entrée en développement (Definition of Ready) : critères d’acceptation et scénarios Gherkin validés en 4 Amigos.
  2. Chaque livraison : tests API et E2E lancés dans la CI ; un échec remonte sur Slack avec le rapport Allure et les responsables tagués.
  3. Chaque nuit : campagne complète de non-régression, analysée le matin, bugs créés et tests maintenus.
  4. Mise en production (GO/NO GO) : validation des parcours critiques et, chez PMU, des transactions financières, des bonus et de la conformité ANJ.
  1. Ready for development (Definition of Ready): acceptance criteria and Gherkin scenarios validated in the 4 Amigos.
  2. Every release: API and E2E tests run in CI; a failure goes to Slack with the Allure report and owners tagged.
  3. Every night: a full regression run, analysed in the morning, with bugs filed and tests maintained.
  4. Production release (GO/NO GO): critical journeys validated and, at PMU, financial transactions, bonuses and ANJ compliance.
